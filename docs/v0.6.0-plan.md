# v0.6.0 native deployment

Status: candidate implemented; 100 local tests at 93.83 per cent coverage, lint, formatting,
strict typing and shell syntax checks pass. No production installation or Pi acceptance yet.

## Scope and sequence

1. Add explicit startup configuration-file support and a managed-service mode that refuses to
   generate or log an administrator token. Bootstrap the token only through an interactive command.
2. Provide a native installer using a dedicated low-privilege account, protected configuration/state,
   immutable versioned virtual environments and a hardened systemd service with restart supervision.
3. Implement explicit backup, upgrade, rollback and non-destructive uninstall. Preserve configuration,
   state and the previous release; no automatic updates or destructive purge.
4. Test configuration loading, token safety, backup validation and deployment assets in CI.
5. Deliver to the Pi and validate permissions, BLE and MQTT under the service account, authenticated
   API access, SIGKILL recovery, graceful shutdown, reboot startup, backup and rollback.

Production paths are /opt/pitboss-admin, /etc/pitboss-admin and /var/lib/pitboss-admin.
The existing /home/john test installation and its databases are never modified automatically.
Initial production configuration uses loopback with token authentication and MQTT disabled.
Trusted-LAN access is an explicit later configuration change, not an installer side effect.
The installer does not overwrite Mosquitto configuration or copy test credentials.
The 16-hour physical soak remains v1.0.0 and is not part of this milestone.

## Candidate handoff

The source archive uses a separate `pitboss-admin-v0.6.0/` root, unlike earlier archives, to avoid
replacing a running editable test installation. Run the candidate quality gate in its own virtual
environment before invoking the privileged installer. Inspect current Pi process, ports and
production-path occupancy first. Installation prints a one-time token: do not ask the user to paste
that output. Ask only for a sanitised success summary. Install leaves production stopped.

Pi acceptance must cover fresh installation, permissions, default unauthenticated rejection,
no token in journal, BlueZ access as the dedicated account, physical probe/display agreement,
write-only MQTT configuration, systemd crash recovery and reboot startup. Take a backup, perform
a same-candidate reinstall via upgrade, then rollback and confirm token, registered identity and
configuration persist. Test non-destructive uninstall/re-enable before release. Retain old releases
and backups; do not clean them up automatically.
