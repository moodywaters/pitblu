# v0.6.0 native deployment

Status: target deployment acceptance passed on 7 September 2026. Local and Pi checks passed
100 tests at 93.83 per cent coverage, lint, formatting, strict typing and shell syntax. CI passed
on Python 3.11, 3.12 and 3.13. Earlier implementation instructions below are retained for context.

## Scope and sequence

1. Add explicit startup configuration-file support and a managed-service mode that refuses to
   generate or log an administrator token. Bootstrap the token only through an interactive command.
2. Provide a native installer using a dedicated low-privilege account, protected configuration/state,
   immutable versioned virtual environments and a hardened systemd service with restart supervision.
3. Implement explicit backup, upgrade, rollback and non-destructive uninstall. Preserve configuration,
   state and the previous release; no automatic updates or destructive purge.
4. Test configuration loading, token safety, backup validation and deployment assets in CI.
5. Deliver to the Pi and validate permissions, BLE and MQTT under the service account, authenticated
   API access, SIGKILL recovery, graceful shutdown, reboot startup, backup and rollback.

Production paths are /opt/pitboss-admin, /etc/pitboss-admin and /var/lib/pitboss-admin.
The existing /home/john test installation and its databases are never modified automatically.
Initial production configuration uses loopback with token authentication and MQTT disabled.
Trusted-LAN access is an explicit later configuration change, not an installer side effect.
The installer does not overwrite Mosquitto configuration or copy test credentials.
The 16-hour physical soak remains v1.0.0 and is not part of this milestone.

## Candidate handoff

The source archive uses a separate `pitboss-admin-v0.6.0/` root, unlike earlier archives, to avoid
replacing a running editable test installation. Run the candidate quality gate in its own virtual
environment before invoking the privileged installer. Inspect current Pi process, ports and
production-path occupancy first. Installation prints a one-time token: do not ask the user to paste
that output. Ask only for a sanitised success summary. Install leaves production stopped.

Pi acceptance must cover fresh installation, permissions, default unauthenticated rejection,
no token in journal, BlueZ access as the dedicated account, physical probe/display agreement,
write-only MQTT configuration, systemd crash recovery and reboot startup. Take a backup, perform
a same-candidate reinstall via upgrade, then rollback and confirm token, registered identity and
configuration persist. Test non-destructive uninstall/re-enable before release. Retain old releases
and backups; do not clean them up automatically.

## Target acceptance, 7 September 2026

- Fresh installation created a non-root account, protected token bootstrap and stopped service.
- Explicit enable/start returned active/enabled; unauthenticated status returned HTTP 401.
- Authenticated discovery and registration worked through BlueZ under the service account.
- Two physical probes matched the device display at 21 Celsius; battery 50 per cent, two absent.
- SIGKILL was followed by one automatic systemd restart and fresh physical polling without reset.
- Ownership/modes matched the design: configuration 0750/0640, state 0700/0600, and the service
  could not write its executable. NoNewPrivileges and ProtectSystem/ProtectHome were effective.
- MQTT credentials were verified and saved through the authenticated write-only API. Retained
  online availability and non-retained physical probe readings were received at QoS 1.
- Protected SQLite backup verified successfully. A same-candidate upgrade created a new release,
  retained the original token and registration, and resumed physical polling and MQTT.
- Rollback selected the preceding release and restored authentication, registration, MQTT and
  fresh probe/battery readings, while creating a safety backup. Cross-version migrations were
  not tested by this same-candidate exercise.
- Pi reboot required no manual service start: enabled service, readiness 200, MQTT connected,
  physical polling and original authentication returned automatically.
- Non-destructive uninstall removed service enablement while preserving protected files.
  Restoring the unit returned active/enabled status, original authentication and fresh readings.
- A local comparison of the supplied administrator token and MQTT password against the available
  service journal found neither plaintext credential. No credentials were copied into evidence.

The production service is running. Its MQTT namespace remains a validation namespace; moving it
to a final topic is an explicit configuration task. The old home-directory source and protected
backups remain on the Pi. Comprehensive security/clean-install audit is v0.9.0; minimum 16-hour
physical soak and full release acceptance are v1.0.0. Neither is claimed complete here.
