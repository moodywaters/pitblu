# v0.5.0 resilience

Status: candidate passed 84 local tests at 93.99 per cent coverage, lint, format and strict typing;
Raspberry Pi acceptance pending

## Implementation and acceptance

1. Supervise MQTT connection failures with safe status, bounded retry backoff, session identity,
   retained-state resynchronisation and bounded offline shutdown.
2. Serialise BLE actions, make duplicate control requests idempotent, cancel recovery on explicit
   disconnect and bypass backoff on reconnect. Restore registered desired connections after restart
   using protected stable identity, never automatic name-only matching to unregistered hardware.
3. Continue after transient reads, degrade after configured failures and reconnect after the
   no-valid-reading deadline. Reset backoff only after stable operation.
4. Persist bounded operational events, mark interrupted operations on restart, expose safe
   diagnostics and stop all tasks before closing resources. Preserve desired connection state.
5. Test recovery, concurrency, persistence, redaction and shutdown with controlled time/fakes.
   Run lint, formatting, strict typing and the coverage gate before Pi delivery.
6. Verify broker restart, invalid credentials, device recovery, explicit disconnect, application
   restart and shutdown on the Pi before release. Do not advance to native deployment.

The current single-adapter service will explicitly reject simultaneous ownership by another device.
Persisting multiple registrations must never permit reading one device under another device ID.
No new runtime dependency is planned. Documentation and handoff updates accompany the code.

## Pi gate

- Install the candidate and pass lint, formatting, strict typing and tests.
- Verify MQTT diagnostics with unavailable broker, then restore the broker and observe recovery.
- Verify a wrong credential gives safe status; correcting the stored secret requires restart.
- Verify a registered simulator restores after application restart; explicit disconnect persists.
- Verify physical V202 power-cycle recovery and probe/display/battery agreement.
- Verify orderly API shutdown with active SSE and offline MQTT retained state.
- Record sanitised evidence before merging, tagging or releasing v0.5.0.

Existing registrations require explicit identity selection before automatic recovery; no name-only
fallback is permitted. Back up the administrative SQLite database before testing the additive
identity migration. The temporary development database and broker credentials stay on the Pi.

## Pi progress, 5 September 2026

The initial candidate passed 84 Pi tests at 93.99 per cent coverage, lint, formatting and typing.
Simulator desired-connected restoration and explicit-disconnect persistence passed after API
restarts. A broker outage produced safe backoff diagnostics and HTTP 503 readiness, then recovered
to HTTP 200 in the same application session. Retained online availability was verified at QoS 1.
An idle publisher detects broker loss on its 60-second heartbeat; a 10-second outage was too short
to demonstrate detection. The longer outage test passed.

Active SSE exposed a shutdown-order defect: Uvicorn waited for the endless response before
application lifespan cleanup and cancelled it at its 15-second deadline. MQTT nevertheless
published retained offline availability successfully. The candidate now closes SSE streams before
Uvicorn drains HTTP requests, leaving internal MQTT subscribers open for offline publication.
A real loopback HTTP regression test checks complete chunked-response termination without the
shutdown timeout. The updated candidate passes 86 local tests at 94.01 per cent coverage.
Pi SSE shutdown retest, invalid-credential testing and physical recovery remain pending.

### Reproduced leftover connection and candidate fix

A controlled SIGKILL left BlueZ reporting Connected: yes. Restarting the API without touching
the iGrill reproduced backoff with no readings. This confirms the recovery gap, but does not
establish the cause of the original overnight process exit.

The candidate now attempts a bounded `bluetoothctl` recovery only when discovery cannot find
the exact persisted identity. It verifies that BlueZ reports that identity connected, disconnects
only that device, checks release, then scans again and performs normal V202 authentication.
Pairing is preserved. It does not reset adapters, remove devices or use name-only matching.
Command output is captured locally and never logged; errors use fixed safe text. This relies on
the existing BlueZ `bluetoothctl` executable and service-account permission to disconnect the device.
Local validation: 92 tests, 93.98 per cent coverage, strict typing. Physical retest is pending.

The first helper candidate did not pass the physical abrupt-stop retest. A subsequent isolated
adapter diagnostic discovered, authenticated and read the registered device successfully, but
another API SIGKILL/restart still failed recovery. Do not claim that releasing BlueZ alone fixed it.
Inspection identified a discovery-cache race: a waiting scan could replace candidates between
recovery discovery and connection. Those steps and the initial read now hold one I/O lock.
A regression test queues a competing scan while recovery is discovering the registered device.
Safe fixed-label `failureStage` diagnostics distinguish discovery, BlueZ release, identity lookup,
connection/initialisation and initial reading failures. No raw exception text is exposed.
Updated local results: 93 tests at 94.01 per cent coverage, lint, formatting and strict typing.
Whether this race explains the physical failure remains unproven until the next Pi test.
